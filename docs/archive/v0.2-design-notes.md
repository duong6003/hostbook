# hostbook v0.2: archived design notes

> Historical architecture record. These notes capture the original v0.2 discussion, including its then-future work and exclusions; they are not the current roadmap or a user guide. See the dated implementation status in [v0.2-implementation.md](v0.2-implementation.md).

This document records only the ideas discussed and the direction agreed at the time. The detailed plan for each area was to be analyzed and finalized in the following session.

## 1. Secret vault (keys and passwords)

- Secrets (SSH keys and passwords) are managed directly in the app, in a **secret vault**.
- The vault is always encrypted, never stored as plaintext on disk, and unlocked with a **master password**.
- The vault syncs through the repository, just like the server list.
- Each secret is **a named entry** (for example, `key-booking` or `matkhau-deploy`), reusable across servers, and tracks which servers use it.
- **References to existing local key files are not supported**, because they cannot be shared. Keys are always imported into the vault.
- Keys are identified by fingerprint to prevent duplicates: pasting or importing the same key again reuses the existing entry.
- External `ssh`, VS Code, and scp can use keys from the vault by unlocking it and loading keys into ssh-agent for a limited time.

## 2. Authentication when adding or editing a server

- Support authentication by **key** or **password**.
- The authentication selector offers:
  - saved secrets, **suggested in advance** based on related servers, with reasons;
  - pasting a new key;
  - importing a key from a path (the app reads its contents into the vault, rather than referencing the file);
  - a new password.

## 3. Editing secrets

- Provide secret management with flexible editing: replace a key (paste or import from a file), generate a new key, edit contents, change a password, copy a public key, rename, see which servers use it, and delete (after warning about affected servers).

## 4. Smart suggestions when adding a server

- Suggestions must **have evidence and show it**. The approach at the time (looking only at the IP range and choosing the majority) was inadequate.
- Agreed direction:
  - score multiple signals: same IP range, shared name prefix, same domain suffix, name words matching tags, recently used projects, and so on;
  - show several leading choices with reasons;
  - suggest the most similar server so its settings can be copied;
  - ask when confidence is insufficient, rather than guessing automatically.

## 5. Sharing

- **Sharing scope = the current search results** (or selected rows). Reuse search; sharing quality depends on the quality of the entered data.
- Sharing is essentially sync restricted by a filter: transfer all relevant servers, tags, descriptions, and groups, **including secrets by default**.
- **No connection between the two machines is needed.** A share package is encrypted text or a file sent through any channel (chat or email); send its password through a different channel.

## 6. Importing a share package

- Provide an **import interface**: preview, then confirm.
- Compare servers individually: skip existing identical entries; for differences, offer update, keep mine, or keep both; warn about duplicate IPs. Deduplicate secrets by fingerprint.
- After import, show a **verification screen** with a summary, then **ask** whether the user wants to check connections to the imported servers. **Do not run checks automatically.**
- Connection checks are also available independently for any servers.

## 7. Interface and themes

- Use fzf's presentation options rather than rewriting the interface in another language.
- Support **multiple list styles** (for example, two-line cards, compact single-line, and minimal), border styles, detail-pane placement, and **color themes** (including light, high contrast, and terminal colors).
- Allow **user customization** through a configuration file and custom themes.
- Offer selection in the app's **Settings** and during **first-time setup**, **with previews**.

## Deferred at the time, outside v0.2

- A team repository where multiple people follow one continuously updated list.
- Multiple hierarchy levels: discussed and rejected because projects, tags, groups, and search were sufficient.
- An English interface.
- Homebrew installation.
- Testing mDNS discovery on a real LAN.
