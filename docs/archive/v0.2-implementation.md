# hostbook v0.2: archived implementation plan

> Historical architecture and implementation record, not a current roadmap or user guide. The requirements and milestone sequence below retain the original plan's meaning. Its implementation status was updated on November 14, 2026; original pending checks, release targets, and exclusions describe that historical planning context, not outstanding work today. Screen mockups and prose labels are translated for this record and are not a promise of English runtime UI.

The original plan was detailed enough for the following session to implement directly. The source discussion is in [v0.2-design-notes.md](v0.2-design-notes.md). All open decisions had been settled in section 1; technical assumptions had been tested in section 2.

The plan used four independently releasable milestones: **M1** secret vault and authentication → **M2** smart suggestions → **M3** sharing, import, and connection checks → **M4** interface and themes. Each milestone required passing tests on macOS and Ubuntu (CI), an updated README, and manual testing of new screens in a real terminal (through tmux, as in earlier work).

## Implementation status (November 14, 2026)

- **M1–M3:** present on the main branch through commit `f8fe0fd` (v0.3.0).
- **M4:** completed in v0.4.0: machine-local configuration, themes, three list styles, an Appearance screen with previews, first-run appearance selection, and preservation of compact style on upgrades.
- Tests: **142 core cases, 108 UI cases, 15 tmux scenarios, and 15 SSH/Docker cases**. Ubuntu and macOS CI both passed ([run 43586621828](https://github.com/duong6003/hostbook/actions/runs/43586621828)). Fresh-install/light-background flows were tested at 60/100/200 columns, along with creating a theme in an editor using temporary data.
- Independent review found and resolved these cases: closing/opening the preview must recalculate list width; Nerd Font support on Bash 3.2; scalar colors containing tabs must be rejected; prod labels must remain visible with long names/tags; and demos must reflect separators and use the same detail-pane visibility threshold. Selectors use the `load` event to select the correct initial value after fzf loads the list.
- M2/M3 macOS CI hung during recovery-code generation because `tr | head` read indefinitely when SIGPIPE was ignored. This was replaced with a bounded read from `/dev/urandom`; tests reproduce that condition without changing recovery-code format or existing secrets.

## 1. Agreed decisions

| Area | Decision |
|---|---|
| Encryption | `age` ≥ 1.3 (with the `batchpass` plugin). The vault uses one age identity; the master password encrypts only that identity |
| Unlocking | Cache the identity in **Keychain** (macOS) or secret-service (Linux). Enter the master password once per machine |
| Forgotten master password | Provide a **recovery code**, shown once when creating the vault |
| Key storage | Only in the vault. Remove the option to reference a local key file |
| Secrets | Named entries reusable across servers; deduplicate keys by fingerprint |
| External ssh | Config pins a `.pub` file; the actual key is in ssh-agent after unlocking (`hb unlock`) |
| Sharing | Text package encrypted with a one-time password; scope = filtered results; **include secrets by default**; no connection between machines required |
| Import | Preview and compare each server; **ask** about connection checks after import |
| Host keys during connection checks | `StrictHostKeyChecking=accept-new`: automatically store keys for previously unseen servers, never accept changed host keys |
| Interface | Use fzf; three list styles, multiple themes, machine-local configuration file (not synced) |
| "Copy key from another machine" tool | **Remove** because the vault replaces it. Keep `ensure_key` (the key for initial access to the repository host) unchanged |
| Servers without a secret | Keep a final choice: "Do not save (let ssh handle it)" for users with their own agent, YubiKey, and so on |

## 2. Trial results (verified on this machine with OpenSSH 10.5, age 1.3.2, fzf 0.75)

| Assumption | Result |
|---|---|
| Password encryption without a TTY | `AGE_PASSPHRASE=… age -e -j batchpass -a` and `age -d -j batchpass` work; a wrong password reports `incorrect passphrase` and exits nonzero |
| Adding a secret without unlocking | `age -e -r "$(cat vault.pub)"` needs only the public key |
| Decrypting with an identity on stdin | `age -d -i - file.age < identity` works; the identity need not be stored on disk |
| scrypt speed | Encrypting and decrypting the identity take ≈ 0.46 seconds |
| Loading a key into the agent without writing a file | `age -d … | ssh-add -q -t 3600 -` works |
| Pinning a key through `.pub` | `IdentityFile x.pub` + `IdentitiesOnly yes` + key in the agent: login works, including through a normal ssh config. Without pinning, an agent with 8 keys causes `Too many authentication failures` |
| `.pub` files require `chmod 600` | With mode 644, ssh prints "UNPROTECTED PRIVATE KEY FILE" when the agent does not yet have the key |
| Before unlocking | ssh prints `Load key "….pub": invalid format`, then `Permission denied` → use this to recognize a locked vault |
| Passwords through askpass | `SSH_ASKPASS=<script> SSH_ASKPASS_REQUIRE=force ssh …` logs in without `sshpass` |
| Detecting passphrase-protected keys | `ssh-keygen -y -P "" -f key` exits nonzero; remove the passphrase with `ssh-keygen -p -P <old> -N "" -f key` |
| Keychain | `security add-generic-password -U -s … -a … -w "$(base64)"`, followed by `find-generic-password -w | base64 -d`, round-trips correctly. Base64 wrapping is required because the identity has multiple lines |
| Agent socket | A socket path longer than ~100 characters makes `ssh-agent -a` fail → place private sockets in `/tmp/hb-XXXXXX/` |
| Allowlist-style `.gitignore` | Adding `!secrets/`, `!secrets/*.age`, `!secrets/*.pub`, `!secrets/*.meta` tracks exactly the required files and ignores unknown files in `secrets/` |
| Share shortcut | `--bind 'ctrl-y:execute-silent(touch MARK)+transform:[ "${FZF_SELECT_COUNT:-0}" -gt 0 ] && echo accept || echo select-all+accept'` returns the matching rows correctly |
| Multiline cards | `fzf --read0` with `--delimiter '\t' --with-nth 2.. --accept-nth 1`: searches the second card line and returns the key in field 1 |
| Terminal-following theme | `--color` accepts ANSI color names (`magenta`, `bright-black`, etc.) and bases `16`, `light`, `dark`, `bw` |
| Parallel checks | 4 parallel connections, one unreachable: total 5.0 seconds with `ConnectTimeout=5` |
| Linux age distribution | The tarball contains `age/age`, `age/age-keygen`, `age/age-plugin-batchpass` |

Unverified at the original planning stage, with a requirement to test at implementation time (using the container in section 8.1): with `SSH_ASKPASS_REQUIRE=force`, host-key confirmation also goes through askpass; section 4.6 forwards that question to `/dev/tty`.

**Pitfalls encountered during trials:** (1) Running `bash <<EOF` containing `ssh` lets ssh consume the rest of the script → all noninteractive ssh commands require `</dev/null`. (2) `eval "$(ssh-agent -a <long-path>)"` fails silently, after which `ssh-add` loads into the user's real agent by mistake → always check `[ "$SSH_AUTH_SOCK" = "$sock" ]` before `ssh-add`; tests must **never** use the real agent (section 8.1).

### 3.3 How servers reference secrets

In `.conf` files, hostbook writes the following (`host_block` changes its sixth argument from a key path to a **secret name**):

```
# tags: prod web
# desc: Primary Nginx
# secret: key-booking
Host a-web1
  HostName 10.0.1.11
  User ubuntu
  IdentityFile ~/ssh-hosts/secrets/key-booking.pub
  IdentitiesOnly yes
```

For a password secret:

```
# secret: matkhau-deploy
Host b-api
  HostName 10.2.0.5
  User deploy
  PubkeyAuthentication no
  PreferredAuthentications password,keyboard-interactive
```

Without a secret: omit `# secret:` and all authentication lines.

- Write `.pub` paths using the actual `$DIR`, shortening `$HOME` to `~`.
- **A server's secret** = its `# secret:` value; if absent, infer it from the effective `identityfile` (`ssh -G`) when it points to `secrets/<name>.pub` (so wildcard blocks can also carry secrets).
- Add **field 12 = secret name** to the index (`index.tsv`). `index_file` reads `# secret:` like `# tags:`; the awk stage after `ssh -G` applies the inference rule above. Retain field 7 (key path) to recognize legacy servers.
- No change to `merge_driver`: `#` lines already belong to the Host block immediately below them.
- Add `secret:<name>` to the hidden suffix of list rows (`cmd_list`) so users can find servers using a secret.
- `cmd_preview`: replace the `IdentityFile` line with `Authentication: key-booking (ed25519 key)`, `…(password)`, or `let ssh handle it`.

## 4. M1: secret vault and authentication

### 4.1 Identity and unlocking

```
vault_exists()    [ -f "$DIR/secrets/vault.pub" ]
vault_id()        first 8 characters of sha256(vault.pub)   # Keychain lookup key
kc_get/kc_set/kc_del  by backend:
   macOS:  security find|add|delete-generic-password -s hostbook -a "vault:$(vault_id)"   (base64-wrapped value)
   Linux with secret-tool: secret-tool lookup|store|clear service hostbook account "vault:<id>"
   Linux without it: file "${XDG_RUNTIME_DIR:-/dev/shm}/hostbook-$UID/identity-<id>" (0600, lost on shutdown);
                    if neither directory exists, do not cache; ask each time
vault_identity()  # print identity to stdout; return 1 if the user cancels
   1. id=$(kc_get); if present and age-keygen -y <<<"$id" == vault.pub → print and finish
      (mismatch: the vault was replaced → kc_del and continue)
   2. ask "Vault master password" (gum input --password), at most 3 attempts;
      AGE_PASSPHRASE=$pw age -d -j batchpass secrets/vault.key.age → id; on failure report "Incorrect master password"
      after 3 failures: ask "Use recovery code?" → vault_recover
   3. kc_set "$id"; print id
```

The identity travels only through pipes/stdin (`age -d -i - file < <(vault_identity)`), never environment variables or command arguments. Changing the master password on another machine does not affect this machine because Keychain stores the identity, not the password.

### 4.2 Creating the vault (`vault_init`)

Invoke automatically the first time a secret is needed (adding a secret or importing a package with secrets), or through `hb vault init`.

```
‹ Create secret vault
The vault stores encrypted keys and passwords and syncs through the repository with your server list.

Master password · at least 10 characters
> ••••••••••••
Enter again
> ••••••••••••
✓ Vault created · this machine will remember it without asking again

╭──────────────────────────────────────────────────────────────╮
│ Recovery code                                                │
│ HB-7K3Q-9XTM-2WPL-R8DC-5VNA                                  │
│ Use if you forget the master password. Save it in a password   │
│ manager or write it down. This code is shown only once.        │
╰──────────────────────────────────────────────────────────────╯
> Saved, continue
  Copy code to clipboard
```

Steps: (1) require matching passwords of ≥ 10 characters; (2) `age-keygen` → identity, `age-keygen -y` → `vault.pub`; (3) `vault.key.age` = batchpass(master password); (4) recovery code = 20 Crockford base32 characters (alphabet `0123456789ABCDEFGHJKMNPQRSTVWXYZ`) from `/dev/urandom`, displayed as `HB-XXXX-XXXX-XXXX-XXXX-XXXX`; batchpass password is the 20 characters without hyphens → `vault.recovery.age`; (5) `kc_set`; (6) commit "Create secret vault" + sync. If the user exits during code display, the vault already exists; print a reminder to run `hb vault recovery-code` to generate a new code.

Immediately afterward, run **migration of keys in use** (4.3).

Subcommands:
- `hb vault passwd`: require the identity (Keychain or old password) → ask for the new password twice → rewrite `vault.key.age`.
- `hb vault recover`: ask for the recovery code → decrypt `vault.recovery.age` → set a new master password → **generate and display a new recovery code** (invalidating the old one).
- `hb vault recovery-code`: require the identity; generate a new recovery code.
- `hb lock [--forget]`: remove hostbook keys from the agent (`ssh-add -d secrets/<name>.pub`); `--forget` also removes the identity from Keychain.
- `hb unlock`: load all key secrets into the agent (4.5).

### 4.3 Migrating keys in use into the vault

After `vault_init`, and in Tools → Secrets while legacy servers remain:

```
Servers currently using keys on this machine:
  ~/.ssh/id_rsa       1 server
  ~/.ssh/id_rsa_dev   3 servers
> Import into vault (recommended)
  Later
```

For each distinct key path in field 7 whose file exists: `secret_add_key <path>` (4.4, default name from the filename), then rewrite config: replace every `IdentityFile X` in `*.conf` where expanded `X` equals that path with `IdentityFile <secrets/name.pub>`, ensuring `IdentitiesOnly yes` in the same block; for non-wildcard blocks, add `# secret: <name>` immediately above Host if missing. Then `validate` → commit "Import N keys into vault". Leave original files in `~/.ssh` untouched. Skip unreadable or invalid keys and report their names.

### 4.4 Adding a secret

`secret_add_key <source>` (source = `clip` | path | `gen`):

1. Read contents into a file in `tmpd`. `clip`: `clip_get`; if it does not contain `PRIVATE KEY`, open `$EDITOR` on an empty file with an instruction line. `gen`: `ssh-keygen -q -t ed25519 -N "" -C "<name>@hostbook"`.
2. Normalize: remove `\r`, add a final newline, `chmod 600`.
3. Validate: successful `ssh-keygen -y -P "" -f f` → no passphrase. Failure due to a passphrase (`ssh-keygen -y -P "" …` reports `incorrect passphrase`) → ask for it (hidden) and remove it: `ssh-keygen -q -p -P <pp> -N "" -f f`. Other failures → "Not a valid private key", stop.
4. `fp=$(ssh-keygen -lf f | awk '{print $2}')`, `keytype` from the last field. If any `.meta` has the same `fp`, print "This key already exists as <x>", return `<x>`, and create nothing.
5. Name: default from the filename (`id_rsa_dev` → `id-rsa-dev`) or key comment; ask using prefilled `ask`; validate the name and ensure it is unused.
6. Write `<name>.pub` (`ssh-keygen -y`, chmod 600), `<name>.meta`, `<name>.age` (`age -e -a -r "$(cat vault.pub)"`). Delete temporary files. Commit through `save_and_sync "Added secret <name>"`.

`secret_add_password`: ask for a name and password twice (hidden); `.meta` contains `type=password`; no `.pub`.

### 4.5 Using keys when connecting

```
agent_ready()     # ensure a usable ssh-agent
   if ssh-add -l returns 0 or 1 → use the existing agent (always available on macOS; manual ssh and VS Code also see it)
   otherwise: read $STATE/agent.env; use that agent if alive; otherwise
              d=$(mktemp -d /tmp/hb-XXXXXX); eval "$(ssh-agent -a $d/a.sock)"; check [ "$SSH_AUTH_SOCK" = "$d/a.sock" ]; write agent.env
load_secret n     # for type=key
   ssh-add -l | grep -qF "$(secret_meta n fp)" && return 0
   vault_identity | age -d -i - secrets/n.age | ssh-add -q -t "$KEY_TTL" -     (KEY_TTL defaults to 28800 = 8 hours; key_ttl setting)
secrets_for h     # secret for h and all jump hosts (recursively through field 6, at most 5 levels)
```

Before invoking ssh, `connect()` calls `agent_ready`; for each secret in `secrets_for h`: key → `load_secret`; password → prepare askpass (4.6). If the user cancels the master-password prompt, print "Vault is locked; connection was not started" and return. `open_many` does this **once in the parent process** for all servers before creating tmux panes so panes do not prompt concurrently.

`hb unlock`: `agent_ready`, then `load_secret` for every key secret; print "Loaded N keys, usable for 8 hours".

Extend `explain()`:
- Log contains `Load key ".*/secrets/.*\.pub": invalid format` and authentication is denied → category `locked`: "Vault is locked on this machine" → action "Unlock and retry".
- `denied` on a server with a key secret: show "Tried: user X, secret <name>" and add "Copy public key for <name>" (to install on the server).
- `denied` on a server with a password secret: "The password saved in <name> is incorrect" → action "Change password for <name>".

### 4.6 Password authentication (askpass)

- `$STATE/askpass` is a two-line script created when needed: `#!/bin/sh` / `exec <SELF> _askpass "$@"`.
- `connect()` sets these for ssh: `SSH_ASKPASS=$STATE/askpass SSH_ASKPASS_REQUIRE=force HB_ASKPASS_HOST=<name> HB_ASKPASS_COUNT=<counter-file-in-tmpd>`.
- `_askpass "$prompt"`:
  1. Prompt contains `yes/no` (host-key confirmation) → print it to `/dev/tty`, read the answer from `/dev/tty`, print to stdout. With `HB_ASKPASS_NOTTY=1` (connection check), print an empty answer.
  2. Prompt contains `assword` → find the secret: extract `user@host` from the prompt, look up the indexed server with `hostname`==host and `user`==user; if none, use the secret of `HB_ASKPASS_HOST`. On the **first prompt** for that secret (tracked in the counter file), decrypt and print it. On **subsequent prompts** (saved password was wrong), ask the user on `/dev/tty`, hide input, and show "The saved password is incorrect"; with `NOTTY`, print an empty answer.
  3. Other prompts (passphrase, OTP, etc.) → forward to `/dev/tty` with hidden input.
- The original first implementation check was to verify that host-key confirmation follows branch 1. If OpenSSH does not route it through askpass, remove branch 1; the rest is unaffected.

### 4.7 Choosing authentication when adding or editing a server

`pick_login <suggestion-context>` → print a secret name, or empty (let ssh handle it); exit 1 on cancellation:

```
Authenticate with
> key-booking        ●●● used by 6 booking servers, same 10.8.1.x range
  key-dev            ●○○ used by 3 project-a servers
  matkhau-deploy     password · 2 servers
  + Paste new key    (copy the key before choosing this)
  + Import key from file
  + New password
  Do not save        let ssh handle it: own agent, YubiKey…
```

- Ordering and reasons come from suggestions (M1: the most common secret in the inferred project first; M2 replaces this with scores from section 5).
- "+ Import key from file": `gum choose` files in `~/.ssh` whose first line contains `PRIVATE KEY`, plus "Other path…" (`gum file`).
- If there is no vault and the selected option needs one, run `vault_init` first.
- `add_host`: change the "Key" row in review to "Authentication"; "Edit one field…" calls `pick_login`. If no suggestion is sufficiently confident (M1: the project has no secrets), ask `pick_login` during the flow before review.
- `host_actions`: add "Change authentication" → `pick_login` → `set_host_secret <server> <name|empty>`: within `block_range`, remove `# secret:`, `IdentityFile`, `IdentitiesOnly`, and (only if the block currently has a password secret) `PubkeyAuthentication no`, `PreferredAuthentications …`; then insert new lines according to 3.3. Run through `apply_change`.
- For a shared `Host a b` line, tell the user to edit with `^e`, as with other actions.

### 4.8 Secret management (Tools → Secrets, or `hb secret`)

List:

```
‹ Secrets                                         vault: unlocked on this machine
> key-booking        ed25519 key · 6 servers · SHA256:egtk…DZgU
  key-dev            rsa key · 3 servers
  matkhau-deploy     password · 2 servers
  key-cu             rsa key · no servers use it
  + Add key (from clipboard)   + Add key from file   + Generate key   + Add password
```

Actions on a secret:

| Action | Approach |
|---|---|
| View servers using it | Return to search with `secret:<name>` |
| Copy public key | `.pub` → clipboard (keys only) |
| Replace with another key | `secret_add_key` under the **same name**; reject a fingerprint matching another secret; remove the old key from the agent; then ask "Install the new key on N servers using it?" (below) |
| Generate replacement key | As above with source `gen` |
| Edit contents | Decrypt into `tmpd` → `$EDITOR` → validate (key: steps 3–4 of 4.4; password: one nonempty line) → encrypt again; do nothing if unchanged |
| Change password | Password secrets only; ask twice |
| Rename | `git mv` the three files; replace `# secret: old` and `secrets/old.pub` paths in `*.conf`; `validate`; one commit |
| Delete | List affected servers; `confirm --default=false`; delete files; remove `# secret:` and authentication lines written by hostbook from affected blocks; remove from agent |

**Install the new key on servers** (optional after replacement; last part of M1): for every server using that secret, jump hosts first:
1. Using the **old key** (still in the agent, pinned through an old `.pub` copy in `tmpd`): `ssh <server> 'umask 077; mkdir -p ~/.ssh; cat >> ~/.ssh/authorized_keys' < <name>.pub`
2. Test the new key: `ssh -o BatchMode=yes -o IdentitiesOnly=yes -o IdentityFile=<name>.pub <server> true`
3. Ask once for the entire batch (default **No**): "Remove the old key from servers where the new key worked?" → `ssh <server> "grep -vF '<old-key-base64-part>' ~/.ssh/authorized_keys > ~/.ssh/authorized_keys.hb && mv ~/.ssh/authorized_keys.hb ~/.ssh/authorized_keys"`
4. Print a ✓/✗ table per server. Failed servers remain unchanged; if installation failed, explicitly state that the new key cannot yet be used there.

### 4.9 Secret sync and conflicts

`commit_all` already runs `git add -A`, so secrets are included. If two machines edit **one** secret, `pull --rebase` fails → existing `conflict` state. Extend `resolve_conflict`: after `git merge`, for each unmerged path under `secrets/`, `ours`/`theirs` mode → `git checkout --ours|--theirs -- <path>` then `git add`; manual mode → ask for each **secret** (take all three `.age/.meta/.pub` files from the same side): "Keep this machine's version / Take repository version".

### 4.10 `doctor`

Add: age version; vault state (not created / unlocked on this machine through Keychain|secret-service|temporary session / locked); secret count and unused-secret count; servers referencing nonexistent secrets (error); legacy servers still referencing key files (warning, suggest 4.3); reset every `secrets/*.pub` with other permissions to `chmod 600`. Remove the permission check for key files in `~/.ssh`.

### 4.11 M1 commands and menu entries

`hb unlock`, `hb lock [--forget]`, `hb secret`, `hb vault init|passwd|recover|recovery-code`. Tools: add "Secrets", remove "Copy key from another machine". Help: add "Secrets". README: add "Secrets" and update "Security" (keys now sync in encrypted form; repository access still requires the master password).

Test hooks: `_vault_init <password>` (no prompts, prints recovery code), `_secret_add_key <file> <name>`, `_secret_add_password <name> <password>`, `_secret_get <name>`, `_set_host_secret`, `_askpass`; `HOSTBOOK_KEYCHAIN=file:<path>` keeps tests away from the real Keychain, and `HOSTBOOK_MASTER=<password>` suppresses `vault_identity` prompts.

## 5. M2: smart suggestions when adding servers

Replace `infer`/`read_infer`/`name_prefix` with an awk program `suggest` (hook `_suggest <address> <name> <user> <port>`), reading `IDX` and `HIST`.

### 5.1 Score each existing server against the new server

| Signal | Points | Reason label |
|---|---|---|
| Same /24 range (IPv4) | 50 | `same 10.8.1.x range` |
| Same /16, different /24 | 15 | `same 10.8.x.x range` |
| Address is a domain name, all labels except the first match | 55 | `same .booking.vn suffix` |
| Domain name, only the root domain matches (last 2 labels; 3 if the last label has 2 characters and the adjacent label ≤ 3 characters, e.g. `com.vn`) | 40 | `same booking.vn domain` |
| Same name prefix (before the first `-`, `.`, `_`, or digit) | 40 | `name starts with bk-` |
| Each other shared name word (split on `-_.` and digits), at most 2 words | 10 | `name contains web` |
| Same non-22 port | 10 | `same port 2222` |
| Same user (when the user explicitly entered one) | 10 | `same user deploy` |
| Used in the last 7 days | 5 | (not shown) |

Within the IP-range group and domain-name group, count only the highest-scoring signal in each.

### 5.2 Project score and confidence

- Project score = sum of its **3 highest-scoring servers**, divided by 1.5 (so one very similar server ≈ three moderately similar servers).
- Confidence: `●●●` ≥ 80 · `●●○` ≥ 45 · `●○○` ≥ 15 · below 15 is hidden.
- Project reason = distinct labels from contributing servers, with server counts: `same 10.8.1.x range (4 servers) · name starts with bk- (5 servers)`.
- **Auto-select** when the top score is ≥ 80 **and** exceeds the second project by ≥ 30. Otherwise, require the user to choose:

```
Which project?
> booking      ●●●  same 10.8.1.x range (4 servers) · name starts with bk- (5 servers)
  project-a    ●○○  same 10.8.x.x range (2 servers)
  + New project
```

### 5.3 Most similar server

For the highest-scoring server, if ≥ 60:

```
Most similar to bk-api (same 10.8.1.x range, name starts with bk-).
Copy bk-api's settings? user duong · key-booking · tags #prod #api
> Yes    No
```

If accepted, take that server's project, user (unless the pasted address specifies one), jump host, and secret; take tags according to 5.4. Review marks these fields `← like bk-api`.

### 5.4 Field values when not copying

- **User**: most common user among the selected project's servers, weighted by score; otherwise the local user.
- **Port**: pasted port, otherwise 22.
- **Jump host**: if ≥ 80% of the project's servers (excluding those tagged `bastion`) use one jump host, choose it.
- **Secret**: most common among the project's servers with the same user; otherwise most common in the project; otherwise empty and ask `pick_login` during the flow.
- **Tags**: tags on ≥ 60% of the project's servers, plus name words matching any existing tag. When editing Tags: `gum choose --no-limit` includes suggested tags (preselected), all other project tags, and "+ Other tag…" for typed input.
- **Name prefix** (prefilled at the name prompt, before a name exists): prefix of the server with the highest address-only score; leave blank below 15 points.

### 5.5 Add-server flow after M2

1. Address (paste) → 2. Name (prefilled prefix with reason) → 3. if a most-similar candidate exists, ask about copying → 4. if project confidence is insufficient, choose a project → 5. if no secret, `pick_login` → 6. review with sources on each field → Save / Edit one field… / Cancel.

Confident case: address, name, accept copy, Save (4 presses of enter). `import_write` (multiline import) uses the same `suggest` without prompts: choose the highest-scoring project if ≥ 15, otherwise `imported`.

`suggest` output (TSV, for testing): `project<TAB>name<TAB>score<TAB>reason`, `peer<TAB>name<TAB>score<TAB>reason`, `field<TAB>user|jump|secret|tags|prefix<TAB>value<TAB>reason`, `auto<TAB>project<TAB>0|1`.

### 6.2 Importing a package

Entry points:
- **Clipboard**: when opening `hb`, if `clip_get | head -c 300` contains `# hostbook-share v1`, ask "Share package in clipboard (12 servers · from Mac). Import?". Ask once per package: store the sha256 of the last offered package in `$STATE/last-offer`.
- `hb import <file>` and Tools → Import multiple servers: `import_flow` recognizes a first line starting with `# hostbook-share` and enters this flow.

Steps:
1. Ask for the package password (visible input because a one-time password may be read over the phone), at most 3 attempts. Decrypt → `tar -xzf` into `tmpd`. Reject packages with paths containing `..` or starting with `/`, and files outside the layout in 6.1.
2. Build the package index: run `index_file` over package `conf/*.conf` with a temporary ssh config that only `Include`s that directory.
3. Classify each packaged server (compare hostname, user, port, jump host, tags, description, secret type and fingerprint, and other option lines):

   | Category | Condition | Recommendation |
   |---|---|---|
   | NEW | Name absent, no duplicate address | add |
   | IDENTICAL | Name exists, all values match | skip |
   | DIFFERENT | Name exists, some values differ | ask |
   | DUPLICATE IP | Name absent but another server has the same hostname and port | ask |

4. Packaged secrets: key fingerprint already exists → reuse the existing secret (map package names to local names). Name exists with a different fingerprint → import as `<name>-2` (increment as needed), clearly marked in preview. Password with an existing name: decrypt the local version to compare; identical → reuse; different → ask "Update / Keep mine (import as <name>-2)". Otherwise → new.
5. Groups: absent → add (members are servers that exist after import); existing → merge membership.
6. Preview:

```
Package from Mac · 12 servers · 2 groups · 2 secrets                ● 3 prod servers

  + 7 new servers             in projects booking (new), project-a
  = 3 identical servers       skip
  ≠ 2 servers differ          ← choice required
      bk-api    HostName 10.8.1.4 → 10.8.1.40
      bk-db     add tag #mysql
  ! 1 duplicate IP            packaged b-api2 shares 10.2.0.5 with your b-api

  Secrets: key-booking (new) · key-dev (already exists, identical)

> Import as recommended       add new, skip identical, ask about each remaining server
  Update all from package
  Keep all of mine            only add new servers
  Review each item…
  Cancel
```

   - For DIFFERENT: show differing lines → "Update from package / Keep mine / Keep both (packaged version becomes `<name>-2`) / Apply this choice to remaining servers".
   - For DUPLICATE IP: "Add as new server / Skip / Replace `<existing-name>`".
7. Apply in **one** `apply_change` (one commit: `Import package from Mac: +7 ~2`): no vault → `vault_init`; write secrets (encrypted to this machine's `vault.pub`, names mapped; update `# secret:` and `.pub` paths in blocks according to the mapping); update = `delete_host_raw <name> keep` then `write_host`; add = `write_host`; merge groups. If `validate` fails, restore the original state as for other operations.
8. Write names of added or updated servers to `$STATE/last-import`. Completion screen (**no automatic connection checks**):

```
✓ Imported: 7 new · 2 updated · 3 skipped · 1 secret

Check connections to the 9 imported servers?
  Each server attempts login and exits immediately, runs no commands, at most 5 seconds.
> Check
  Later
  View imported servers
  Undo this import
```

   "View imported servers": open filtered search (`home` accepts a name-list file; `cmd_list` prints only those names; header says "Viewing 9 imported servers · esc to view all"). "Undo" = `undo_last` (because import is one commit).

### 6.3 Connection checks (`check_hosts <name>…`)

Entry points: after import; a server's `→` menu ("Check connection"); the multi-server `→` menu (6.5); `hb check [query…]`. Always initiated explicitly by the user. Above 30 servers, the question must state the count.

1. Split `explain()` into `classify_log <name> <log>` → print `category<TAB>one-line reason` (existing logic), and frame rendering. `check_hosts` uses `classify_log`.
2. Prepare: `agent_ready`; load every required key (unlock once).
3. Layer by jump host: layer 0 = servers without a jump host, or whose jump host is not in this check; layer k = servers whose jump host is in layer k−1. If a jump host fails, mark all dependents `· skipped: jump host <x> unreachable` without attempting them.
4. For each server, in parallel batches of 8:
   - key secret or no secret: `sshx -v -E <log> -o BatchMode=yes -o ConnectTimeout=5 -o StrictHostKeyChecking=accept-new <name> true </dev/null`
   - password secret (BatchMode disables password authentication): omit `BatchMode`, set `SSH_ASKPASS_REQUIRE=force HB_ASKPASS_NOTTY=1` and `-o NumberOfPasswordPrompts=1`
   - hard limit: stop the process after 8 seconds and classify as timed out.
5. Live display: one line per server (`⣾ connecting…` → `✓ authenticated with key-booking` / `✗ <one-line reason>`), redraw in place every 0.2 seconds. If server count exceeds screen rows, show only counters `✓ 41 · ✗ 3 · 12 remaining`, then list failures on completion.
6. Save `$STATE/last-check.tsv` (name, result, reason, log path retained in `$STATE/tmp`). Final menu: "View error details" (select server → full error frame from saved log) / "Retry failed servers" / "Done".

### 6.4 M3 commands

Test hooks: `_share_build <output-directory> <include-secrets-0|1> <names…>` (build unencrypted package directory), `_share_pack <password> <names…>` (print package), `_import_classify <package-directory>` (print classification TSV), `_import_apply <package-directory> <theo-gói|giữ-của-tôi>`, `_check <names…>` (print result TSV without rendering).
